- Review cycle 2 repair batch:
  - `prepare_with` is serialized by a prepare mutex (`BackendManager::prepare_lock`, exposed through `UpdateHost::prepare_lock`), held for the whole run inside the `spawn_blocking` closure. Invariant: `Ok` means the guard passed under the latch and the sidecar is stopped. A second prepare sees the first one's final outcome: latch held -> prepared (Ok without re-running the guard); latch released -> it acquires, re-runs the guard and refuses too. Deterministic test `a_prepare_overlapping_a_refusing_prepare_does_not_return_ok` (verified to fail without the mutex).
  - `backend_restart` (`restart_clearing_update`) returns `update_in_progress` while a prepare holds the mutex (try_lock), so a restart cannot slip between the latch and the stop.
  - `stop_for_update` publishes its Failed note without touching `worker_active` (it owns no startup slot); a worker's tail release is `release_worker_slot(worker_id)` and never clears a newer worker's slot (test added). Test renamed `the_update_latch_blocks_starts_until_cancelled`.
